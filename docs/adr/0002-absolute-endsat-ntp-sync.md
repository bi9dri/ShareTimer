# ADR 0002: タイマー状態を絶対時刻 endsAt で表し、NTP 方式で同期する

- 日付: 2026-10-10
- 状態: 承認済み

## 文脈

複数端末が同じ残り時間を表示し、同じ瞬間にアラームを鳴らす必要がある。残り秒数をサーバが配信・定期加算する方式は、ネットワーク遅延・再送・サーバのタイマー精度で端末ごとのズレが蓄積する。また端末の時計はサーバとズレており、単純な一方向補正では片道遅延が混入する。

## 決定

### 状態は絶対時刻で持つ

サーバは残り秒数ではなく、タイマー終了の**絶対時刻 `endsAt`（epoch ms）** を保持・配信する。`serverTime` を各状態に同梱し、各端末はローカルに残り時間を計算する。

### オフセットは NTP 方式で推定する

`offset = serverTime - Date.now()` の 1 サンプルは片道遅延を含む。代わりに:

1. クライアントは `GET /api/time?t0=<epochMs>` に送信時刻 `t0` を送る。
2. サーバは自分の時刻 `ts` を返す。
3. クライアントは受信時刻 `t1` を記録し、`offset = ts - (t0 + t1) / 2`、`rtt = t1 - t0` を求める。
4. 複数サンプルのうち**最小 RTT** を採用する（非対称遅延の影響が最小）。
5. 接続時・定期（15〜30 秒）・**期限直前（T-5s など）**に再計測する。

残り時間は `remaining = endsAt - (Date.now() + offset)`。同時鳴動の目標精度は数十 ms（下限は `offset` 推定誤差 ≒ RTT/2）。

## 影響

- 良い: 遅延・再送・端末数の増加に対して残り時間がズレない。
- 良い: 端末の時計がズレていても正しく表示でき、端末間で鳴動時刻が揃う（[ADR 0003](0003-client-side-alarm.md)）。
- 良い: 端末がローカルで残りゼロを判定できるため、サーバのタイマー精度に依存せずアラームが鳴る。
- 悪い: 端末側に `offset` の管理と再同期が必要で、`GET /api/time` の往復が要る。
- 注意: `paused` は `endsAt` を持てないため `remainingMs` を別途保持する。`running` と `paused` で表現するフィールドが異なる。
